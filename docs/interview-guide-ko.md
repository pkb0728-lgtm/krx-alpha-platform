# 면접 답변 가이드

이 문서는 KRX Alpha Platform을 포트폴리오 면접에서 설명할 때 사용할 수
있는 답변 모음입니다. 답변은 외워서 말하기보다, 프로젝트의 설계 의도를
자연스럽게 설명하는 기준으로 사용하면 좋습니다.

## 1분 소개

```text
KRX Alpha Platform은 한국 주식 데이터를 기반으로 한 설명 가능한 투자
의사결정 보조 플랫폼입니다. 단순히 내일 주가를 맞히는 예측기가 아니라,
가격, 수급, 공시, 재무, 뉴스, 거시 데이터를 수집하고 ETL로 정리한 뒤,
시장 국면과 종목별 점수, 리스크 필터를 적용해서 사람이 다시 검토할
후보를 만드는 시스템입니다. 결과는 Streamlit 대시보드와 Telegram
요약으로 확인할 수 있고, 실제 주문은 보내지 않는 Human-in-the-loop
구조로 설계했습니다.
```

## 왜 만들었나요?

주가 예측만 하는 프로젝트는 실제 운영 관점에서 부족하다고 생각했습니다.
실제 투자 판단에는 데이터 수집, 품질 검증, 리스크 관리, 설명 가능성,
검증, 알림, 운영 자동화가 함께 필요합니다. 그래서 단일 모델보다
운영 가능한 금융 데이터 분석 플랫폼을 목표로 만들었습니다.

## 왜 단순 가격 예측이 아닌가요?

주가의 정확한 가격을 맞히는 것은 어렵고, 작은 기간에서는 과최적화되기
쉽습니다. 이 프로젝트는 가격 자체보다 다음 질문에 답하는 것을 목표로
합니다.

- 지금 시장 국면이 위험한가?
- 이 종목은 기술적/재무/뉴스/수급 관점에서 상대적으로 우호적인가?
- 리스크 필터를 통과했는가?
- 사람이 다시 검토할 만한 근거가 있는가?

즉, “정답 가격”보다 “확률적으로 검토할 가치가 있는 상황”을 찾는 구조입니다.

## 전체 아키텍처 설명

```text
데이터 수집
-> raw 저장
-> processed 정제
-> feature 생성
-> market regime 분석
-> scoring
-> risk filter
-> final signal
-> auto screener
-> backtest / paper trading
-> dashboard / Telegram / reports
```

핵심은 각 단계를 분리한 것입니다. 수집, 가공, 피처, 신호, 리스크,
리포트가 분리되어 있어 유지보수와 테스트가 쉽고, 중간 산출물을 재사용할
수 있습니다.

## 데이터 흐름 설명

데이터는 계층별로 저장합니다.

| 계층 | 의미 |
| --- | --- |
| `data/raw` | API나 라이브러리에서 가져온 원본 데이터 |
| `data/processed` | 타입, 결측치, 날짜 등을 정리한 데이터 |
| `data/features` | RSI, 변동성, 거래대금 변화 등 재사용 피처 |
| `data/signals` | 점수, 최종 신호, 스크리너 결과 |
| `data/backtest` | 백테스트와 페이퍼트레이딩 결과 |

이 구조 덕분에 문제가 생겼을 때 어느 단계에서 깨졌는지 추적할 수 있습니다.

## 어떤 API를 사용했나요?

사용한 데이터 소스와 API는 다음과 같습니다.

- pykrx: 한국 주식 가격/거래 데이터
- OpenDART: 기업 공시와 재무 데이터
- 네이버 검색 API: 뉴스 데이터
- Gemini API: 뉴스 요약/감성 분석 확장 기반
- FRED: 거시경제 데이터
- 한국투자증권 KIS 모의투자 API: 모의계좌 잔고 조회와 후보 계산
- Telegram Bot API: 일일 요약 알림

무료 또는 무료 플랜 중심으로 구성했고, API 키는 `.env`에만 저장하도록
설계했습니다.

## 리스크 필터는 왜 중요한가요?

투자 보조 시스템에서 가장 위험한 것은 점수만 보고 매수 후보를 많이
만드는 것입니다. 그래서 최종 신호 전에 리스크 필터를 적용했습니다.

예를 들어 다음 조건이 있으면 후보에서 차단합니다.

- 단기 변동성이 너무 높음
- 하루 변동폭이 큼
- 위험 점수가 약함
- 시장 국면이 고변동성 또는 하락장
- 데이터가 부족하거나 신호 파일이 비어 있음

이 프로젝트는 후보를 많이 만드는 것보다, 위험한 상황에서는 쉬는 판단을
내리는 것을 더 중요하게 봅니다.

## 후보가 0개면 실패 아닌가요?

아닙니다. 후보 0개는 정상 결과일 수 있습니다.

```text
이 시스템은 매일 반드시 매수 후보를 만드는 도구가 아닙니다.
점수, 신뢰도, 리스크 기준을 모두 통과한 종목만 검토 후보로 만들고,
조건이 부족하면 후보 없음으로 남기는 보수적인 구조입니다.
```

예를 들어 최신 `large_cap` 실행에서는 10개 종목이 모두 정상 처리됐지만,
스크리너 통과 종목은 0개였습니다. 셀트리온은 가장 가까운 후보였지만
신뢰도와 스크리너 점수가 기준보다 낮아 탈락했습니다. 이 결과는 오류가
아니라 리스크 관리 관점의 정상 판단입니다.

## KIS 모의투자는 실제 주문인가요?

아닙니다. 현재 구현은 실제 주문을 보내지 않습니다.

KIS API는 다음 목적으로만 사용합니다.

- 모의투자 토큰 발급
- 모의계좌 잔고 조회
- 스크리너 결과와 계좌 정보를 결합한 검토 후보 계산

실제 주문 API 호출은 구현하지 않았습니다. 실수로 실제 매매가 나가지 않게
하고, 사람이 최종 판단하는 구조를 명확히 하기 위해서입니다.

## 백테스트와 워크포워드는 왜 넣었나요?

신호가 좋아 보이는 것과 실제 과거 데이터에서 검증되는 것은 다릅니다.
그래서 백테스트와 워크포워드 검증을 넣었습니다.

- 백테스트: 최종 신호가 과거 가격에서 어떤 수익/손실을 냈는지 확인
- 워크포워드: 특정 기간에만 맞는 전략인지, 구간을 나눠 반복 검증
- 거래비용/슬리피지: 현실적인 비용 반영

현재는 MVP 수준의 검증 구조이며, 상용 실행 시뮬레이터는 아닙니다.

## ML 모델은 어떤 역할인가요?

현재 ML은 핵심 의사결정 엔진이라기보다 baseline입니다. 단순한 가격 예측이
아니라, 향후 초과수익 가능성이나 상승 확률을 확률형으로 추정하기 위한
흐름을 만들었습니다.

중요하게 고려한 점은 다음과 같습니다.

- `as_of_date` 기준으로 미래 데이터 누수 방지
- 학습 데이터와 라벨 분리
- TimeSeriesSplit/Walk-forward로 시계열 검증
- 복잡한 모델보다 설명 가능한 baseline부터 시작

향후에는 LightGBM, 앙상블, SHAP 기반 설명을 붙일 수 있습니다.

## 대시보드와 텔레그램은 왜 필요한가요?

분석 결과가 파일로만 남으면 실제로 쓰기 어렵습니다. 그래서 운영 흐름을
만들었습니다.

- Streamlit 대시보드: 종목 순위, 스크리너, 리스크, KIS 후보, 백테스트 확인
- Telegram: 장 마감 후 한국어 요약 알림
- Markdown reports: 포트폴리오 제출과 기록용 결과물

즉, 데이터 분석 코드에서 끝나는 것이 아니라 사용자가 매일 확인할 수 있는
운영 화면까지 연결했습니다.

## 보안은 어떻게 관리했나요?

API 키와 토큰은 GitHub에 올리지 않도록 설계했습니다.

- 실제 키는 `.env`에만 저장
- `.env.example`에는 빈 예시만 제공
- `.gitignore`로 `.env`, `.cache`, 데이터 산출물, 로그 제외
- KIS 토큰 캐시는 `.cache/kis_paper_token.json`에 저장하고 Git에서 제외
- 에러 메시지에서 민감값을 redaction 처리
- GitHub Secrets 사용을 문서화

보안 점검으로 실제 키, 토큰, 계좌번호 패턴이 Git에 없는지도 확인했습니다.

## 테스트와 품질 관리는 어떻게 했나요?

현재 프로젝트는 다음 품질 도구를 사용합니다.

- `pytest`: 기능 회귀 테스트
- `ruff`: 린팅
- `ruff-format`: 포맷팅
- `mypy`: 타입 검사
- `pre-commit`: 커밋 전 품질 검사
- GitHub Actions: 원격 CI

최근 기준 전체 테스트는 `pytest`로 통과 여부를 확인합니다.

## 현재 한계

솔직하게 말할 수 있는 한계는 다음과 같습니다.

- 상용 자동매매 시스템은 아님
- 실제 주문 API는 구현하지 않음
- 유니버스는 아직 정적 목록 중심
- 시장 국면 분석은 긴 lookback이 필요함
- ML 모델은 baseline 수준
- 뉴스 감성/공시 이벤트 해석은 더 고도화 가능
- 장기간 실거래 수준의 성과 검증은 아직 부족

이 한계는 프로젝트의 실패가 아니라, MVP에서 운영형 플랫폼으로 확장하기
위한 다음 단계입니다.

## 향후 개선 방향

- KOSPI200/KOSDAQ150 자동 유니버스 구성
- 관심종목 파일 기반 실행
- 업종별 비교 분석
- 시장 지수 기반 regime 분석 강화
- LightGBM/앙상블 모델 추가
- SHAP 기반 설명 가능성 강화
- 장기 백테스트와 포트폴리오 제약 추가
- Windows 작업 스케줄러로 장 마감 후 자동 실행
- README에 대시보드/텔레그램 스크린샷 추가
